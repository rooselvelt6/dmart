2. Resumen ejecutivo y glosario

2.1 Resumen ejecutivo

dMart UCI es una plataforma clínica hospitalaria que unifica en un único binario compilado en Rust toda la operación de una Unidad de Cuidados Intensivos. El sistema fue diseñado para entornos exigentes y, en particular, para “red hospitalaria aislada sin acceso a internet”: no depende de servicios en la nube, todo el ciclo de vida del dato (ingesta, persistencia, cifrado, cómputo de escalas, inferencia de modelos, auditoría) ocurre dentro del hospital.

El frontend se compila a WebAssembly y se ejecuta en el navegador con el framework reactivo Leptos: la misma lógica de cómputo clínico (escalas, validaciones, modelos) está compartida entre el backend y el frontend desde un crate común (dmart-shared), lo que elimina la duplicación de lógica y los desajustes entre cómo se calcula un score en el servidor y cómo se muestra en pantalla.

El desarrollo siguió la metodología Spec-Driven Development (SDD): 46 especificaciones formales, cada una con tests de conformidad dedicados, cobertura medida y validación en el pipeline CI antes de cada entrega.

Resultado medible: 210 pruebas del backend en verde (82 unitarias + 128 de integración) en el gate de cobertura, 20 tests E2E end-to-end pasando, gate de cobertura >= 60 %, fuzzing continuo de tres componentes críticos y un dataset de demostración a escala con 520 pacientes en menos de 3 segundos de siembra.

3. Contexto y problema clínico

3.1 El problema

Las Unidades de Cuidados Intensivos operan con pacientes en estado crítico cuyo deterioro puede producirse en minutos. La vigilancia clínica depende de datos complejos: constantes vitales provenientes de monitores de cama, escalas de gravedad estandarizadas, historial acumulado y guías de práctica. Sin una plataforma integrada, este trabajo se realiza con hojas de cálculo, papel y sistemas fragmentados que no conversan entre sí, lo que genera:

  • Datos dispersos: cada monitor, laboratorio y servicio conserva su propia base sin consolidación.
  • Cálculo manual de escalas: APACHE II, GCS, NEWS2, SOFA y SAPS III se puntúan a mano, con riesgo de error y sin reutilización histórica.
  • Retraso en la alerta: la detección de un paciente que se deteriora depende de la frecuencia de las rondas.
  • Ausencia de interoperabilidad: los monitores emiten HL7 v2, pero el hospital no tiene quién lo interprete y persista.
  • Riesgo de privacidad: la PHI viaja sin cifrar ni registro de quién la consultó.
  • Sin trazabilidad: no existe auditoria inmutable de accesos y modificaciones.

3.2 La propuesta de valor

dMart UCI resuelve estas carencias con un único sistema autocontenido:

4. Metodología: Spec-Driven Development (SDD)

4.1 Qué es SDD

Spec-Driven Development (desarrollo guiado por especificaciones) es una metodología en la que cada requirerimiento funcional o no funcional del sistema se redacta primero como una especificación formal (“spec”) y solo después se implementa, se prueba y se valida contra esa especificación. A diferencia de un documento de requisitos pasivo, cada spec en este proyecto tiene una entidad de control: se exige un formato mínimo (objetivo, alcance, decisiones, criterios de aceptación, riesgos), se valida en CI (“Spec Lint / SDD Gate”) y no puede cerrarse sin los tests de conformidad y cobertura asociados.

La metodología garantiza que ninguna funcionalidad queda sin enunciar, que el código es trazable a un documento y que el estado de avance (specs aprobadas, tests verdes) es medible en todo momento.

4.2 Por qué se eligió para un sistema clínico

  • Auditabilidad: cada función clínica tiene un documento de referencia; es la base ideal para evidencia normativa (HIPAA/ISO 27001).
  • Seguridad por defecto (fail-closed): cada spec de seguridad define el comportamiento seguro como caso por defecto y los tests lo comprueban.
  • Calidad medible: el pipeline exige lint de specs, clippy -D warnings, tests y cobertura por módulo.
  • Colaboración clínico-técnica: un médico puede validar la definición de una escala antes de que se programe.

4.3 El flujo SDD aplicado en el repositorio

1. Definición      spec-XXX en `specs/` (formato validado por el SDD Gate)
2. Validación     CI: `Validate spec format`, lint, revisión obligatoria
3. Implementación  Código Rust/Leptos trazable a la spec
4. Tests          cargo test -p dmart-server --lib --test api_tests
5. Cobertura      cargo llvm-cov -p dmart-server --lib --test api_tests  (gate >= 60 %)
6. Conformidad    HL7/FHIR/scales con tests de conformance dedicados (SPEC-028, specs HL7)
7. Entrega        imagenes multi-stage, Helm, GitOps (ArgoCD/Flux)

5. Stack tecnológico y conceptos aplicados

Este capítulo explica, para cada tecnología del sistema, qué es, cómo funciona por dentro y de qué manera concreta se aplica en dMart UCI.

5.1 Rust (2024 edition)

Qué es: un lenguaje de programación de sistemas enfocado en rendimiento y seguridad de memoria. El compilador impide, en tiempo de compilación, los errores clásicos de C/C++ (use-after-free, carreras de datos, desbordamientos) mediante el sistema de propiedad y préstamos, sin necesidad de un recolector de basura.

Cómo se aplica: todo el backend (servidor HTTP Axum, parser HL7, cifrado, auditoría, ML) y toda la lógica compartida están escritos en Rust. El perfil de release usa opt-level="z", LTO y strip para minimizar el binario (un único ejecutable que aloja API + frontend estático + listener de monitores). Características de seguridad directas: tipos Zeroizing para secretos (borran la memoria al soltarse), comparación en tiempo constante con subtle, y ausencia de GC (latencias deterministas para la ingesta de monitores).

5.2 WebAssembly (WASM)

Qué es: un formato binario de bytecodes portátil que se ejecuta en una máquina virtual integrada en los navegadores. Permite compilar código de sistemas (C, C++, Rust) y ejecutarlo a velocidad casi nativa en el cliente, con un modelo de memoria aislado (sandbox).

Cómo se aplica: la aplicación de interfaz (dmart-app) se compila con Trunk a un módulo WASM de aproximadamente 3,2 MB (dmart-app-*-_bg.wasm) y un pequeño pegamento JavaScript. Al abrir el sistema, el navegador instancia el WASM y ejecuta toda la aplicación: ruteo, reactividad, i18n, temas y llamadas a la API. El resultado es una SPA rápida que funciona sin framework JavaScript en el host y que es instalable como PWA para operar sin una conexión a internet estable.

5.3 Leptos 0.8 (framework reactivo)

Qué es: un framework de interfaz de usuario escrito en Rust que compila a WASM. Su modelo es la reactividad por señales: los datos se envuelven en Signal y la interfaz se declara como una función de esas señales; cuando una señal cambia, solo las partes dependientes se recalculan y se vuelven a renderizar (sin algoritmos de reconciliación masiva).

Cómo se aplica: las 17 rutas de la SPA (login, panel, pacientes, expediente, medición, timeline, CDS, escalamiento, dispositivos, calidad, administración, soporte, tenants, auditoría y perfil) están declaradas en app.rs con protección de ruta por rol. El estado de sesión se mantiene en señales globales: el access token vive únicamente en memoria (nunca en localStorage) y se renueva por cookie httpOnly; la identidad (nombre/rol para mostrarse en la barra) sí se persiste de forma segura. El sistema es multilingüe (es, en, fr, pt) y tiene tres temas (claro, oscuro, sistema).

5.4 Axum 0.8 (framework web)

Qué es: el framework HTTP asíncrono del ecosistema Tokio/Tower para Rust: routers tipados, extracción de argumentos por tipos, middlewares componibles y soporte de streaming (SSE, WebSockets).

Cómo se aplica: el servidor monta el API versionado (/api/v1 y ruta heredada /api), el router de observabilidad (/obs/health, /obs/live, /obs/ready, /metrics) y el servicio de estáticos del frontend desde dist/. Los middlewares de seguridad (rate limiting, throttle de login y de MFA, cabeceras de seguridad) son capas de Tower sobre el router. El streaming SSE de eventos clínicos sale del mismo proceso.

5.5 SurrealDB (SurrealKV embebida)

Qué es: una base de datos multi-modelo (documentos, grafos y consultas tipo SQL llamadas SurrealQL) distribuible. En su modo embebido (SurrealKV) funciona como una librería dentro del proceso del servidor, sin procesos externos.

Cómo se aplica: se persiste en el archivo local data/dmart.db. Provee transacciones atómicas para ingresos/egresos, múltiples tablas (patient, measurement, user, refresh_token, audit_event, hl7_ingest_key, tenant, ...) y 27 migraciones versionadas en SurrealQL que evolucionan el esquema de forma ordenada (desde 001_baseline_indexes.surql hasta la más reciente). Para alta disponibilidad, las specs definen un cluster SurrealDB de 3 nodos en Kubernetes.

5.6 Server-Sent Events (SSE)

Qué es: un canal HTTP unidireccional donde el servidor empuja eventos al cliente de forma continua. A diferencia de WebSocket, es más simple y robusto en proxies que filtran por HTTP.

Cómo se aplica: el módulo realtime.rs mantiene un hub de conexiones SSE (con máximo 10 por IP para evitar acaparar el hub). Cuando se ingiere una medición (manualmente o desde un monitor HL7), el evento se emite a los clientes suscritos, filtrado por tenant, y el panel actualiza las tarjetas de cama al instante.

5.7 PWA / Service Worker / Web Push

Qué es: Progressive Web App: una web con manifiesto, service worker y APIs de notificaciones que se puede instalar y usar offline.

Cómo se aplica: el manifiesto y el service worker (sw.js) se copian al dist/; el frontend declara las APIs PushManager/PushSubscription (SPEC-052) y el backend las suscripciones con claves VAPID para enviar alertas de escalamiento a los dispositivos, incluso cuando la app no está en primer plano.

7. Modelo de datos y protección de PHI

7.1 Modelo de datos (SurrealDB)

El esquema evoluciona con 27 migraciones SurrealQL versionadas. Las tablas principales se agrupan por dominio:

DominioTablas / registros
Pacientespatient (expediente, cédula, historia clínica, estado, gravedad, scores), patient_event (timeline), admission/historial de camas.
Clínicomeasurement (constantes y escalas), vectores de referencia clínica para validación de rangos.
Identidaduser (staff), refresh_token, audit_event, sesiones MFA.

Las claves únicas compuestas (p. ej. tenant_id + message_id en hl7_ingest_key) dan idempotencia a la ingesta: si un monitor reenvía el mismo mensaje (mismo MSH.10), se responde el ACK idempotente sin duplicar la medición.

7.2 Cifrado de PHI en reposo

La información de salud identificable nunca se guarda en claro:

  • Envelope vigente DMART_A2: cada campo PHI se cifra con AES-256-GCM (cifrado autenticado: detecta cualquier alteración). Se usa un envelope con clave por registro (DEK) derivada de una clave maestra, de forma que diferentes registros con la misma cédula no tengan el mismo texto cifrado (nonce aleatorio de 12 bytes).
  • Envelope legacy DMART_V1: ChaCha20-Poly1305. Se conserva para descifrar datos antiguos y se detecta automáticamente por el "magic" del sobre (backfill transparente).
  • Subclaves HMAC-SHA256: la clave maestra se deriva en subclaves etiquetadas LABEL_PHI y LABEL_INDEX, separando cifrado de datos y cómputo de índices.
  • Claves en memoria: los secretos se guardan en Zeroizing (cero al soltar) y el proveedor de claves (KeyProvider) permite rotación sin downtime anotando el key_id por envelope.

7.3 Índices ciegos y búsqueda sin exponer PHI

Para permitir consultas rápidas sin escribir texto en claro en disco, el sistema calcula HMAC-SHA256 (clave = subclave de índice) de la cédula, historia clínica, nombre exacto y de los trigramas del nombre normalizado (campo bi_tng). Una búsqueda:

  1. Normaliza la consulta (mayúsculas, sin tildes),
  2. calcula los trigramas y sus HMAC,
  3. busca filas candidatas por coincidencia de trigramas (solo se comparan HMAC, nunca texto),
  4. descifra los pocos candidatos y los ordena con Jaro-Winkler en Rust, con bonificación por prefijo y coincidencia exacta.
Efecto: se puede buscar "gus", "jorg" u "ortiz" y tolerar erratas de teclado, sin que un atacante con acceso al disco pueda leer ningún nombre paciente.

8. Autenticación, autorización y RBAC

8.1 Autenticación

El sistema aplica un esquema de sesión de tokens de corta vida con renovación segura:

MecanismoDetalle
ContraseñasHash con Argon2id (parámetros OWASP), nunca en claro, con fuerza validada (min. 12 caracteres por política, rechazo de placeholders).
Access tokenJWT HS256 de 15 minutos con expiración, claim tenant_id, lista de permisos y versión; revocable. Vive solo en memoria del navegador.
Refresh token7 días, persistido en cookie httpOnly + SameSite=Strict; rota en cada renovación y se revoca en logout. El hilo de sesión lo renueva cada 10 minutos.
Segundo factorMFA TOTP RFC 6238 (ventana de 30 s, tolerancia de deriva) con códigos de respaldo de un solo uso; flujo de challenge antes de entregar token.
Anti fuerza brutaThrottle de login, throttle específico del flujo MFA y rate limit global; en producción el límite se distribuye con Valkey/Redis (INCR + EXPIRE atómicos).

8.2 Autorización basada en roles (RBAC)

El modelo define roles y permisos granulares. Cada endpoint verifica el permiso requerido desde el token; no basta "estar autenticado".

RolPermisos claveUso típico
AdminTodos (*), gestión de usuarios, camas, equipos, tenants, auditAdministración del sistema y de la unidad

Enfermeropatients:read, measurements:create/read, escalamientoIngreso de constantes y vigilancia de cama

Cada acceso a un recurso verifica además la pertenencia al tenant (require_tenant_ownership): un usuario de un hospital no puede leer pacientes de otro aunque tenga el rol adecuado. En el frontend, la barra lateral muestra u oculta opciones según permisos (user_has(...)) y las rutas protegidas redirigen ante falta de permiso.

8.3 Flujo de ingreso interactivo

  1. El profesional introduce usuario y contraseña en la vista de login.
  2. El backend valida Argon2id; si el usuario tiene MFA activo devuelve un challenge.
  3. La interfaz muestra el paso TOTP (o código de respaldo).
  4. Con el challenge resuelto se entrega access token (memoria) + refresh (cookie) y la app navega al panel.
  5. El panel carga estadísticas, censo y suscripción SSE.

9. Seguridad del perímetro y capas de defensa

9.1 Frontera MLLP (monitores de cama)

MLLP es un protocolo de texto plano sobre TCP: sin protección, las constantes vitales viajarían en claro y cualquier host de la red podría inyectar datos. La frontera se endurece en capas:

  • mTLS obligatorio en producción: TLS 1.3 exclusivo, cifrado únicamente AES-256-GCM (TLS13_AES_256_GCM_SHA384), certificado de cliente verificado contra la CA propia de monitores, no contra la CA pública.
  • Pinning de identidad: el fingerprint SHA-256 del certificado se vincula al MSH.3 que la conexión declara (DMART_MLLP_CLIENT_IDS). Un monitor no puede hacerse pasar por otro.
  • Handshake de secreto compartido (DMART_MLLP_AUTH_SECRET) como capa 2 cuando no hay mTLS; comparación en tiempo constante y buffer Zeroizing.
  • Allowlist de emisores sobre MSH.3, bind por defecto a loopback.
  • Anti slow-loris: timeouts de lectura/escritura y tope de conexiones global y por IP.
  • Fail-closed: sin mTLS ni handshake, el listener no arranca en despliegues productivos.
  • Idempotencia: deduplicación por MSH.10 con clave UNIQUE (tenant, message_id) y ACK de rechazo para mensajes inválidos.

10. Algoritmos clínicos: escalas de gravedad

Los cálculos de escalas viven en dmart-shared/src/scales.rs, compartidos entre servidor y frontend, con vectores de referencia clínica (SPEC-028) que validan rangos normales y críticos en tests y en la consola de calidad de datos.

10.1 APACHE II (Acute Physiology And Chronic Health Evaluation II)

Qué es: el sistema de clasificación de gravedad más extendido en UCI (Knaus et al., 1985). Estima la probabilidad de mortalidad hospitalaria a partir de datos fisiológicos del primer día de ingreso.

ComponenteRango de puntosDetalle
Acute Physiology Score (APS)0-6012 variables: temperatura, PAM, frecuencia cardíaca, frecuencia respiratoria, oxigenación (PaO2/a/A), pH arterial o HCO3, sodio y potasio sérico, creatinina, hematocrito, leucocitos y GCS corregido.
Puntuación por edad0-6Escalones desde <=44 años (0) hasta >=75 años (6).
Enfermedad crónica grave0-5Insuficiencia orgánica crónica o inmunodepresión, con restricciones quirúrgicas/electivas.

Total máximo: 71 puntos. La probabilidad de mortalidad hospitalaria se obtiene con una función logística sobre el score y el grupo diagnóstico (la implementación incluye la fórmula y su constante de regresión).

10.2 Escala de Coma de Glasgow (GCS)

Qué es: mide el nivel de conciencia (Teasdale & Jennett, 1974) puntuando tres respuestas.

ComponentePuntosDescripción
Apertura ocular1-4Espontánea (4), a la voz (3), al dolor (2), ninguna (1).
Respuesta verbal1-5Orientado (5)... ninguna (1); intubados se codifican como "1T".
Respuesta motora1-6Obedece órdenes (6)... ninguna (1).

Total: 3-15; menor de 8 suele indicar coma y alerta para asegurar vía aérea.

10.3 NEWS2 (National Early Warning Score 2)

Qué es: sistema de alerta temprana del Royal College of Physicians (2017) para detectar deterioro clínico con datos de cabecera.

ParámetroPuntos por desviación
Frecuencia respiratoria, SpO2, tensión arterial sistólica, pulso, conciencia (CVPU) y temperatura0-3 por parámetro según rango; +2 si se requiere oxígeno suplementario.
EscalaTotal 0-20; umbrales de alerta en 5 (bajo), 6-7 (medio) y >=8 (alto).

En el sistema, NEWS2 alimenta el streaming EWS por cama: cada medición nueva lo recalcula y si supera umbral se dispara el escalamiento.

10.4 SOFA (Sequential Organ Failure Assessment)

Qué es: puntúa la disfunción de seis sistemas de órganos (Vincent et al., 1996); cada sistema aporta 0-4 puntos.

SistemaPuntosVariable proxy
Respiratorio0-4PaO2/FiO2 (relación de oxigenación)
CoagulaciónPlaquetas
HepáticoBilirrubina
CardiovascularPAM / vazoactivos
NeurológicoGCS
RenalCreatinina o diuresis

Total 0-24. Normal < 5; >=5 se asocia a disfunción multiorgánica.

10.5 SAPS III (Simplified Acute Physiology Score III)

Qué es: score de admisión (Moreno et al., 2005) con variables fisiológicas, demográficas y de admisión (origen, motivo, comorbilidades, uso de vasopresores, GCS): total 0-217, convertido a probabilidad de mortalidad hospitalaria. En el sistema es uno de los scores que se calculan al registrar una medición con los datos soportados.

Validación clínica automática: los tests usan vectores de referencia con pacientes "normales" y "críticos" (p. ej. SAPS III normal < 30, crítico >= 50; NEWS2 normal < 5, crítico >= 10; SOFA normal < 5) y fallan si el cálculo no se ajusta a esos límites (fixtures en dmart-shared/testdata/scales).

11. Inteligencia artificial y machine learning

11.1 Ensemble de mortalidad hospitalaria

El módulo ml_ensemble.rs combina tres modelos para estimar la probabilidad de mortalidad durante la hospitalización:

Modelo baseRol
DecisionTree (linfa)Captura interacciones no lineales entre variables y es interpretable (reglas).
Regresión logística (GLM binomial)Referencia lineal calibrada en probabilidades.
Gradient BoostingRefuerza la precisión sobre residuos del conjunto.
Stacking (opcional)Meta-modelo que combina las salidas de los base.

Las probabilidades crudas de cada modelo se calibran (isotónica o Platt scaling, resolviendo el problema de la singularidad de la matriz con regularización) para que el valor de salida sea una probabilidad honesta: un riesgo del 0,80 significa realmente 80 % en la población de calibración. Las features provienen de ml_features.rs (escalas, constantes y datos demográficos).

11.2 Red neuronal de estancia (LOS)

El módulo ml_los.rs predice la Estancia (Length of Stay). Usa un backend de tensores candle 0.8:

  • Arquitectura MLP multi-capa con window fija sobre el historial de mediciones y capas recurrentes opcionales (LSTM/GRU).
  • Entrenamiento con descenso de gradiente (Adam) sobre múltiples épocas, con dropout para regularizar y normalización de entradas.
  • Pesos persistidos y cargables (ModelWeights) para rehidratar el modelo sin retraducción.
  • Métricas de inferencia expuestas a Prometheus.

11.3 Motor de similitud de pacientes

El módulo similarity.rs (SPEC-033) genera embeddings clínicos de 128 dimensiones mediante feature hashing de las variables del paciente y calcula coseno entre vectores para devolver los top-K pacientes más parecidos (con explicación por feature y scope de tenant). La API ofrece búsqueda, explicabilidad, estado y regeneración de embeddings. Es una base para "pacientes como éste" en el CDS.

11.4 Forecasting de operaciones

El módulo forecasting.rs produce proyecciones de ocupación y estancia con cuantiles normales (naive forecaster implementado sobre statrs), usado por los paneles de administración y los scripts de costos (cost_forecast.sh).

Serving: ml_serving.rs implementa un registro de modelos (Predictor trait) con swap en caliente vía API (/ml/models/swap), batch inference y métricas ml_inference_*. La especificación contaba también con un backend de inferencia sobre ONNX/WASM (SPEC-032).

12. Interoperabilidad y tiempo real

12.1 HL7 v2 + MLLP

Los monitores de cama emiten mensajes HL7 v2 (el estándar de mensajería de salud más desplegado en equipos médicos). El tipo de mensaje soportado es ORU^R01 (Observation Result Unsolicited), que transporta las observaciones (constantes y parámetros) de un paciente.

Protocolo MLLP: encuadra cada mensaje HL7 entre un byte de inicio (0x0B VT), el bloque de datos y un bloque de fin (0x1C FS + 0x0D CR). El parser ASN.1-like de hl7/parser.rs interpreta los segmentos (MSH, PID, OBR, OBX...), valida el MSH.10 (idempotencia), aplica control de calidad (ingest/quality.rs: plausibilidad de rangos) y persiste la medición. Los ACK de aceptación y rechazo siguen las reglas de HL7.

El sistema incluye drivers por fabricante (Mindray, Philips y genérico) que normalizan el mapeo de código de observación a las escalas internas, y backpressure: si el sistema se satura, la ingesta regula la tasa y abre un circuit breaker ante fallos repetidos (recuperable desde la consola de soporte o automáticamente HalfOpen).

12.2 FHIR R4

El módulo fhir_bundle.rs genera recursos FHIR R4 para el intercambio institucional:

Recurso FHIRContenido emitido
PatientExpediente del paciente (identificadores, demografía) con PHI ya protegida por política de export.
Observation (LOINC)Constantes y escalas codificadas con LOINC.
Condition (CIE-10)Diagnósticos con códigos CIE-10 (p. ej. I63.9, I60.9, G61.0).
DiagnosticReport / BundleInformes y paquetes para consumo externo (hv, sistemas institucionales).

12.3 Streaming de alertas tempranas (EWS)

El módulo ews_stream.rs combina las escalas (NEWS2/APACHE/SOFA) con las últimas mediciones de cada cama y emite el estado por SSE. Las conexiones se limitan por IP, se filtran por tenant y el panel las consume para pintar tarjetas en vivo. La especificación SPEC-014 garantiza además que el streaming siga funcionando cuando llegan datos de varios monitores a la vez.

12.4 Tele-UCI

El módulo teleicu.rs permite a un centro remoto observar el estado agregado de la unidad (espejo de censo y alertas) respetando el aislamiento de tenant y los permisos, pensado para modelos de tele-intensivismo.

13. Auditoría WORM, timeline, búsqueda y calidad

13.1 Auditoría inmutable (WORM)

audit.rs implementa un registro de auditoría con garantía de no manipulación:

  • Cadena encadenada: cada evento incluye el prev_hash (SHA-256) del anterior; la génesis es un hash de 64 ceros.
  • Lotes firmados: los eventos se agrupan en lotes de hasta 1.000 registros firmados con HMAC-SHA256 usando subclave derivada. Alterar un evento invalida su hash, el siguiente eslabón y la firma del lote.
  • Concurrencia segura: la escritura está serializada con tokio::Mutex; ninguna operación introduce huecos.
  • Retención: 6 años, con tarea de limpieza POST /api/admin/audit/cleanup y verificación de integridad de la cadena en la exportación.
  • Visor forense: el frontend muestra la cadena y permite copiar el resumen del export (SPEC-049).

13.2 Timeline clínico append-only

El patient_timeline.rs construye la línea de tiempo del paciente (ingreso, mediciones, planes CDS, egreso) como eventos de solo añadido. Cada evento tiene un fingerprint criptográfico, de modo que cualquier edición o borrado posterior es detectable. Esto complementa la auditoría WORM con la vista clínica temporal.

13.3 Búsqueda de pacientes

Ya descrita en 7.3: normalización, trigramas ciegos (HMAC), reducción de candidatos y ranking difuso Jaro-Winkler con bonificaciones. Soporta búsqueda parcial por pocas letras, nombres con espacio, apellidos, tildes y erratas; exige como mínimo 3 caracteres para el camino difuso y cae a coincidencia exacta por debajo (por cédula, historia o nombre).

13.4 Calidad de datos

El módulo data_quality.rs audita el dataset: completitud (campos requeridos por registro), plausibilidad (rangos fisiológicos por escala y variable), integridad referencial (mediciones sin paciente válido, camas huérfanas) y consistencia de scores (que la escala calculada coincida con la persistida). La consola muestra el estado por métrica y permite accionar correcciones. El validador de ingesta comparte estas reglas (ValidationReason) antes de aceptar una medición.

15.1 Cómo se ejecutan

# Relevant tests del backend (rápido)
cargo test -p dmart-server --test api_tests --test hl7_integration
cargo test -p dmart-server --lib

# Coverage gate (>= 60 % global + por módulos)
cargo llvm-cov -p dmart-server --lib --test api_tests

# E2E UI
npm run test:e2e          # Playwright contra el servidor levantado

# Carga
k6 run tests/load/auth.js tests/load/scales.js
Regla operativa: en este repositorio nunca se ejecuta cargo test --workspace en local porque compila el frontend WASM y el fuzzing (horas); el backend se valida con los targets acotados anteriores (~15 s) y el resto lo resuelve el CI.

15.2 Especificación 027 - Gate de cobertura

SPEC-027 define el gate: cobertura global >= 60 % medida con llvm-cov, verificada por check-coverage-thresholds.sh con umbrales por módulos. El pipeline falla (rojo) si no se alcanza, impidiendo que código sin probar llegue a producción. El badge del repositorio refleja el último estado del gate.

16.3 Operación y runbook

  • Arranque: validar variables críticas, secretos, iniciar dmart-server y comprobar los logs (DB conectada, listeners, servidor en :3000).

  • Consola de soporte: subsistemas, acciones y self-healing descritos en 14.14.

17. Despliegue, GitOps y continuidad

17.1 Build multi-stage

El pipeline produce una imagen de contenedor multi-stage: etapa de compilación Rust (host), build del frontend WASM (Trunk) y etapa final slim con el único binario y el dist/ incrustado. La imagen se firma con cosign keyless y se escanea con cargo deny/cargo audit en CI.

17.2 Kubernetes / Helm

RecursoFunción
Deployment dmart-serverReplicas del API+frontend con HPA, probes de liveness/readiness, PDB e Ingress TLS.
StatefulSet SurrealDBCon o sin cluster de 3 nodos (SPEC-023) y volumen persistente.
NetworkPolicy / ServiceAccountSegregación de red y mínimo privilegio.

17.3 GitOps (ArgoCD / Flux)

El repositorio incluye manifiestos ArgoCD (AppProject + Application) y Flux (GitRepository + HelmRelease + Kustomization). El flujo es: cambio en el repo -> CI verde -> imagen firmada -> GitOps sincroniza el cluster. Los scripts deploy_blue_green.sh, deploy_canary.sh y deploy_rollback.sh implementan estrategias de liberación con verdes/azules y canario con regresión rápida.

17.4 Entornos

Se mantienen tres perfiles de configuración (dev, staging, prod) con variables separadas. En prod: CORS cerrado, cookies seguras, HSTS, MFA obligatorio, rate limit distribuido (Valkey) e ingesta MLLP con mTLS y fail-closed. En desarrollo se usan desactivaciones explícitas (rate limit, throttles) marcadas como tales.

El evidence pack (docs/compliance/) cataloga controles aplicables: A.5 (políticas), A.8 (gestión de activos y PHI), A.9 (control de acceso: RBAC, mínimo privilegio), A.10 (criptografía), A.12 (operaciones: backup, logs, vuln management) y A.14 (desarrollo seguro: SDD, CI, revisión). Los scripts compliance_generate.sh/compliance_check.sh generan y verifican el pack como parte de CI.

19.3 FDA SaMD y protección de datos

  • FDA Software as a Medical Device: la lógica de cómputo de escalas está en un crate de dominio validado por vectores de referencia clínica y tests de conformidad, sentando la base de un expediente de validación de software.
  • GDPR / LOPD: minimización (solo PHI necesaria), cifrado, índices ciegos, derecho de acceso mediante export, retención definida (auditoría 6 años) y registro de decisiones automatizadas (ML) expuesto y explicable.
Dato relevante: las especificaciones 034 y 039 definen el pack de evidencia (control catalog, data flows, incidentes, marco legal y backfill de PHI) de modo que la evidencia normativa se genera y se valida de forma automatizada.
